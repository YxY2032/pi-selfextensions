# 实战篇：给失忆专家配一块白板——Plan 扩展的完整实现

> 本文是《Agent 设计第一性原理：用 pi 拆解一切》的实战章。前面十二章在拆别人的机器；这一章自己上机床——用全书讲过的零件，从零造一个真实功能，再把成品（661 行、8 个文件、62 个测试）逐件拆给你看。写法不变：先考题，后答卷；先现象，后机制。

---

## 引子

你刚做过一个实验：给 pi 派了一个长任务——"检查电脑文件、排查入侵痕迹、写清理脚本、输出报告"。任务下达的瞬间，屏幕上跳出这样两行字：

```text
plan 4 steps · 检查电脑文件构成、排查入侵痕迹、产出无害清理脚本并输出最终报告
plan: 4/4 done · 2 updated
```

第一行出现的时机是**模型自己**决定的——没有谁强迫它列清单。最后一行意味着四步全部完成、它自己给自己打了勾。任务结束时，这几行字消失了，像一块用完擦掉的白板。

问题来了：模型是个无状态纯函数（序幕），它凭什么"自觉"？那几行字背后，代码到底做了什么？这一章就是把这块白板拆开——它挂在哪、谁擦谁写、为什么压缩撕不走它、以及为什么只需要 708 行。

## 承上

前面十二章造好的机器，跟本章相关的有五件：

- **申请单协议**（第一章）：模型想做事，只能递结构化申请单；申请单必带回执；
- **循环与轮**（第二章）：谁递单、谁入卷、什么时候停，全由循环调度；
- **会话树与双读者**（第五章）：一切落盘为只追加的记录；"给模型看的"和"给用户看的"是两次不同的组装；
- **压缩**（第六章）：模型视野会被折叠成摘要——**这是长任务记忆的头号杀手**；
- **扩展系统**（第九章）：pi 的理念是"最小内核 + 极宽扩展缝"，第三方功能一律从扩展缝长出来。

而 pi 现状里其实藏着一块**退化版的任务记忆**：压缩摘要模板里的"进展三态"栏（第六章考题 3）。它的问题有三个：低频（只在压缩时才更新一次）、低质量（靠总结员事后回忆）、被动（模型平时根本看不见它）。实战篇要造的，就是把它升级成一块**高频、权威、模型随时可见**的白板——学名叫 Plan（执行工作记忆，见仓库 CONTEXT.md 的术语表，别跟"Plan Mode 只读规划模式"混淆）。

## 通用原理：任何"长链路任务"功能绕不开的六道考题

**反事实：如果没有它会怎样？**

给模型一个跨五步的任务，走到第三步：案卷已经很长（注意力稀释——重要的旧指令在新噪声里沉底），或者刚经历一次压缩（第三步之前的细节被折叠成摘要）。模型的典型病相：跳步（"我以为那步做完了"）、重复劳动（把第一步又做一遍）、提前收工（"大功告成"——其实还有两步没干）。**没有外置工作记忆的 agent，本质上只能做"一口气能憋完"的任务。**

**它到底解决什么问题？**

把"我做到哪了"从模型的脑内回忆，变成一份**它每轮开工前都会重新读一遍的外部文件**。注意措辞：不是"帮模型记住"——模型永远记不住（序幕第一性原理）——是**每次都重新给它看**。

**设计它必须回答的考题：**

1. **白板挂哪？**——记忆的权威副本放在什么地方，才能既跟着会话走、又不怕压缩、还能在分叉时自动正确？
2. **模型怎么读写？**——一个工具还是多个操作？"改一步"和"重排全部"是一回事吗？
3. **白板怎么回到模型视野？**——靠模型翻案卷找旧回执，还是每轮主动递到眼前？压缩发生的那一刻谁负责？
4. **谁保证推进到完成？**——模型提前收工时，放行还是催工？催工会不会变成死循环？
5. **人类怎么看见？**——用户不问模型的话，屏幕上有几处能看到进度？
6. **代码放哪、怎么装进 pi？**——改内核还是做扩展？怎么分发？

## 我们的答卷

**考题 1 的答案：白板挂在"回执的备注栏"里。**

第一章讲过 pi 的私货设计：工具回执分"内容"和"详情"两部分——内容进模型视野，详情（details）只有界面和日志用。本扩展的全部状态，就存在 `write_plan` 回执的 **details 备注**里：`{改之前的计划, 改之后的计划}`。

为什么挂这里而不是单独建个状态文件？三个理由，每个都对应一条全书原理：

- **压缩免疫是白送的**：第六章——压缩只折叠"发给模型的"（内容），从不删"存进文件的"（记录）。白板住在记录里，压缩撕不走；
- **分支正确是白送的**：第五章——会话树按父子指针回溯。重启或切分支时，代码沿当前分支**从后往前**找最后一张 write_plan 回执，读它的备注——站在哪个叶子，读出哪块白板，零额外管理；
- **不发明第三本账**：pi 的铁律是状态只住在案卷记录里（第十一章 three stores 不变式的产品层投影）。住在 details 里 = 不给系统添新账本。

**考题 2 的答案：一个工具，全量重写。**

`write_plan` 只有一个动作：**每次调用都交出完整的计划**（目标一行 + 全部步骤），像重抄整张白板，而不是擦掉某一行。为什么不做"加一步/勾一步/删一步"四个小操作？重排、拆步、合并这些复杂编辑，在全量重写下都退化为"再抄一遍"；而在增量操作下要发一串申请单，模型容易漏发、留下脏清单——全行业三家参考实现（Claude Code、Gemini、OpenCode）独立收敛到了同一答案，这是有原因的。

申请单照例要过审批（第一章流水线）：步骤数上限 20（防清单失控）、每步 200 字内（逼一步一个可验证结果）、有步骤必须有目标。**校验失败不默默丢弃，而是带回执带指引**（"步骤 3 超过 200 字；把每步写成单一可验证结果"）——还是第一章的铁律：模型在等回执，坏的回执也好过石沉大海。

**考题 3 的答案：简报员每轮开工前抄一遍板。**

pi 有个官方检查点：`before_agent_start`——每次你提交消息、新一轮工作开始之前。扩展就蹲在这里，把当前计划抄成一段 20 行以内的 `<plan_state>` 塞进系统提示：

```text
<plan_state>
Goal: 检查电脑文件并输出报告
1. [x] 检查文件构成
2. [>] 排查入侵痕迹
3. [ ] 编写清理脚本
4. [ ] 汇总报告
</plan_state>
```

为什么不等模型自己去翻案卷里的旧回执？两个理由：案卷会变长，旧回执会沉底；更致命的是压缩会把回执从视野里裁掉——**恰好是最需要记忆的时刻失忆**。而每轮注入的成本（二十行）可以忽略，所以不需要任何"陈旧度优化"。全部完成时，快照会换台词："报告结果，然后擦板（发空步骤列表）"——这就是退休路径，擦板是显式动作，不是悄悄消失。

**考题 4 的答案：落定亮灯，不代驾。**

模型提前收工（说"完成了"但板上有空格）怎么办？pi 有个事件叫"运行落定"（agent_settled）——重试、压缩、排队都清零，机器真正停下那一刻。扩展蹲在这里做两查：板上还有空格吗？最后停止原因是"正常说完"吗（被你 Escape 或出错的不查——第四章的分诊纪律）？通过，就在页脚亮一盏警告灯：`plan 2/4 · unfinished`。**仅此而已——它不替你按继续键。**

为什么如此克制？这一题藏着本篇最重要的一课。第一版实现的是"催工"：落定后自动往对话里递一条"继续推进"，替用户发起下一轮（烧的是用户的 token）——当时自我辩护为"需求本体"。严苛复审把它推翻了：pi 的宪法里**续跑永远由人发起**（第四章：Enter 是转向、队列由人触发），一个扩展在用户眼看着机器停下之后又替用户踩了油门，哪怕只踩三脚、哪怕用的是官方认可的 API——"用被认可的 API 做出 API 作者未必预期的自主行为"和"符合设计理念"是两回事。**灯亮着，方向盘还你手里。**

**考题 5 的答案：三个橱窗。**

折叠时一行摘要（`plan: 1/3 done · +1 step`），展开看变更明细（`~ 1. [ ]->[x] 某步骤`，只显示变化行）；编辑器上方常驻挂件（目标 + 未完成步骤，完成即隐藏）；`/plan show` 弹窗看全量。外加 `/plan`（强制重列）和 `/plan clear`（手动擦板——会往会话树落一条"已擦板"标记，重启后仍然记得擦过）。

**考题 6 的答案：独立包，引用式安装。**

不改内核一个字（第九章：能走扩展缝就不动内核）。做成独立目录，一条 `pi install ./路径` 装入——本地路径是**引用不拷贝**，改代码重启即生效。五个核心依赖（工具协议、TUI 组件等）放 peerDependencies 声明"pi 自带，不重复购买"。这就是官方生态里 pi-subagents 那类第三方包的标准形态。

## 一次真实任务的完整旅程（就是你自己跑的那个审计任务）

```text
你输入长任务
→ 模型看到 write_plan 说明书里的判据（≥3 步/跨文件/多轮工具调用才建板）
→ 递申请单：write_plan(goal=审计, steps=[4 步全部 pending])
→ 柜台校验通过，回执入卷，details 存下整块白板
→ 界面渲染折叠行 "plan 4 steps · …"；挂件亮起
→ 每轮开工前，简报员把快照塞进系统提示——模型永远"进门先看板"
→ 模型干完一步：再递全量申请单（该步标 completed）→ 翻译官算出 diff 渲染 "~ 3. [>]->[x]"
→ [假如此时压缩发生] 回执被折叠出视野——下一轮快照从 details 重建，照常进门
→ 〔若提前收工：落定亮灯 plan 2/4 · unfinished，续不续由你决定〕
→ 4/4：快照换退休台词 → 模型输出报告，递空列表擦板
→ 注入停止，挂件熄灭，页脚归零。会话文件里，这一切都是可回放的记录
```

## 小结与部件清单

| 部件 | 分级 | 说明 |
|---|---|---|
| 权威副本存回执 details | **S**（概念） | 压缩免疫 + 分支正确 + 不加新账本，一石三鸟 |
| 全量重写工具 | **A** | 三家参考实现共同收敛的答案 |
| 每轮开工前注入快照 | **S**（对长任务） | 记忆的本质是"每次重新给看"，不是"存住" |
| 落定标记（亮灯不代驾） | **B** | 复审砍掉了自动催工；把续跑权还给用户 |
| 三重视图 | **B** | 挂件是体验质变件 |
| 独立包分发 | **C** | 生态层的标准姿势 |

总量：**661 行源码 / 8 文件 / 62 个测试 / 0 行内核改动**。

### 值得偷师的三件

1. **双读者红利的第二种用法**：details 本来是"给界面看的备注"，拿来做状态存储，白捡压缩免疫和分支正确——好协议的红利总在设计者的意料之外；
2. **重文案、轻代码**：这个功能一半的"智能"住在 prompts.ts 那 200 词里（判据、纪律、退休台词）。prompt 就是控制面，改一句话就能改变模型行为，比改代码便宜一个量级；
3. **严苛复审要能推翻自己的裁定**：初版"封顶催工"在宽松标准下是"需求本体"，在 pi 的主权原则下是越权——评判尺子从"业界怎么做"换成"这套系统的宪法说什么"，结论就会翻转。改卷子之前，先确认自己拿的是对的那把尺子。

## 启下

这块白板只解决"进门看板"，没解决两件事：**判断力**（"这任务值不值得建板"是模型行为，弱模型会失手——所以留了 `/plan` 手动兜底）和**跨会话**（隔天继续属于 Ticket 台账层，两层别混）。下一课的自然选题：把这块板接上真正的长链路——多会话、多工位的 wayfinder 工作流。
